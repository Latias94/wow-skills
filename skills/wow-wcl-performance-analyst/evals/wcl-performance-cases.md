# WCL Performance Analyst 回归用例

这些用例用于检查技能是否会做出可验证、场景化的判断，而不是测试固定措辞。

## 用例 1：同场两个元素萨满

输入：同一 H 难度首领的完整事件 JSON、伤害表和两个源 ID；两人都有四件套，装等接近。

必须做到：

- 先比较战斗时长、存活、任务和团队增益。
- 拆出先祖/复制体、核心技能、施法密度和小怪目标分配的贡献。
- 发现减冷却天赋、自动补 DoT 或爆发自动触发后，再判断技能次数；不能仅凭“次数少”判定漏按。
- 识别爆发是否错过小怪波次、流电/顺劈目标是否不同，并给出相对时间证据。
- 把死亡造成的损失与循环损失分开。

## 用例 2：只有线上链接，事件不可访问

输入：公开 WCL URL，但当前环境只能打开排名页。

必须做到：

- 说明当前只能做摘要级判断。
- 请求最小本地导出：战斗元数据、伤害表、施法/增益事件；不要要求 API 密钥。
- 不编造技能时间线、覆盖率或“高手起手顺序”。

## 用例 3：开荒夜多次灭团

输入：同一报告中多个未击杀尝试和死亡事件。

必须做到：

- 切换为进度模式，使用中位数、趋势和阶段到达率。
- 对每次尝试过滤团队级联死亡，重点分析前两次死亡。
- 只在玩家稳定到达的阶段做高手对比。

## 用例 4：构筑不同但任务不同

输入：玩家带辅助天赋负责打断/驱散，基准玩家没有该任务。

必须做到：

- 把任务差异列为可比性限制。
- 不把所有 DPS 差距归因于天赋或循环。
- 分别报告伤害、功能性和生存价值。

## 用例 5：经验沉淀

输入：3-5 场相同首领、不同击杀时长的高分样本。

必须做到：

- 按阶段/机制编号对齐，而不是只按绝对秒数。
- 只把重复出现的动作写成稳定经验卡。
- 记录版本、构筑、证据数量、容错边界和验证指标。
