# WCL 输入契约

这份文件用于判断“当前数据足够分析到哪一步”，不是要求用户一次性提供所有文件。

## 在线报告

从 URL 解析：

- 报告代码：`/reports/<code>`。
- 战斗编号：查询参数 `fight=<id>`；没有时先列出报告中的战斗。
- 玩家源 ID：查询参数 `source=<id>`；没有时从参与者列表按角色名匹配。
- 页面筛选（`type`、`view`、`hostility` 等）只能作为提示，不能代替实际事件数据。

在线分析的最小顺序：报告元数据 → 战斗列表 → 参与者/专精 → 伤害表 → 施法事件 → 增益/减益与死亡事件。页面只给出排名或总伤害时，必须标记为“摘要级分析”，不能声称已经核对了技能时间线。

## 本地文件

优先识别以下常见形状：

| 文件形状 | 关键字段 | 可支持的分析 |
| --- | --- | --- |
| WCL 事件响应 | `events`, `nextPageTimestamp` | 时间线、施法、目标、增益、死亡、资源 |
| WCL 伤害表 | `entries`, `totalTime` | 总伤害、技能占比、命中次数、目标拆分 |
| WCL 战斗元数据 | `fights` 或 `startTime/endTime` | 难度、击杀、阶段、时长、战斗筛选 |
| 分析器已整理 JSON | `fight`, `player`, `events`, `summary` | 直接复盘；仍需核对原始字段 |
| CSV/文本导出 | 标题行 + 时间/技能/数值 | 仅在字段含义明确时使用，先说明限制 |

事件时间戳通常是毫秒绝对时间；如果文件中出现相对秒数或微秒，先通过战斗时长和相邻事件间隔判断单位，不要静默换算。

## 数据完整度分级

- **A 级：完整复盘**：战斗元数据、事件、伤害表、玩家详情、天赋/装备至少有四类。可以分析爆发轴、目标选择、资源和死亡因果。
- **B 级：核心复盘**：事件 + 伤害表，缺少排名或完整装备。可以找技能执行差距，但不能严谨判定构筑收益。
- **C 级：摘要复盘**：只有伤害表/截图。可以比较伤害构成和技能次数，不能断言具体空窗、覆盖率或死亡原因。
- **D 级：方向性建议**：只有链接但无法访问，或只有 DPS。先给需要补充的最小字段，不要编造时间线。

## 在线获取与分页

若环境具备 WCL v2 API：

1. 从环境变量或安全凭据存储读取客户端凭据，不从对话中索取或输出密钥。
2. 事件查询必须持续读取 `nextPageTimestamp`，直到为空；分页起点要严格递增。
3. 对重叠分页按时间戳、事件类型、来源、目标、技能和数值去重。
4. 缓存报告代码、战斗编号和查询类型，避免重复抓取；遇到限流时退避，不并发轰炸接口。
5. 线上数据与本地数据冲突时，保留两者并说明时间、筛选条件和来源，不能悄悄覆盖。

如果没有 API 权限，优先使用用户已提供的公开页面；若页面无法显示事件，转为本地导出流程。不要因为“能打开报告首页”就假设能读取所有事件。

## 本地摘要工具

对较大的 JSON，运行：

```powershell
python scripts/summarize_wcl.py --events <events.json> --table <damage-table.json> --source-ids <id1>,<id2> --fight-id <fight>
```

可重复传入 `--events` 合并分页或不同玩家事件文件。如果只有带 `source` 参数导出的单角色伤害表，使用 `--table-source-scoped`；不要把单角色表同时用于多个 source。脚本会输出 `schema_version`、战斗时长、有效存活时间、伤害构成、施法次数、增益时长、目标拆分和死亡事件。摘要中的 `cast_gap_candidates_seconds` 只是需要回看的候选空档，不是自动判定的漏按。

## 隐私与安全

- 本地文件默认只在本地处理，不上传到外部服务。
- 报告若为私密或未公开，回答中只引用用户指定的角色和战斗。
- 不输出访问令牌、客户端密钥、未参与问题的玩家隐私或完整原始日志。
- 写入经验文件、缓存或报告前，先得到用户明确要求；默认只在对话中给出可复制结果。
