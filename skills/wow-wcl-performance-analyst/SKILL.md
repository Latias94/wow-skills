# WoW WCL 表现分析师

## 核心定位

这是一个“日志证据 → 机制解释 → 训练动作”的分析技能。它不只报 DPS 排名，也不把单个高手的按键顺序机械照搬给用户。最终要回答四件事：

1. 差距到底来自哪里：装备、构筑、战斗轴、技能执行、目标选择、资源、生存，还是团队分工。
2. 哪些观察是日志事实，哪些是基于机制的推断，哪些仍然需要更多日志或模拟验证。
3. 高分样本中哪些规律可以迁移，哪些只是特定队伍、击杀时长或战术造成的偶然现象。
4. 用户下一把只需要练什么，以及用哪些 WCL 指标确认确实变好了。

默认使用中文技能名和中文解释；第一次出现的英文原名、ID 或缩写只用于对照。不要把英文技能名堆在正文里。

## 适用输入

支持三种输入模式，可混合使用：

- **在线报告**：用户提供 `warcraftlogs.com` 或 `cn.warcraftlogs.com` 报告链接，可附 `fight`、`source`、角色名或首领名。
- **本地导出**：WCL/分析器导出的事件 JSON、伤害表 JSON、施法表、增益/减益表、战斗元数据或打包目录。优先识别 `events`、`entries`、`combatantinfo`、`fight` 等字段。
- **混合模式**：本地事件用于精确时间线，在线页面用于排名、天赋或样本筛选。

在线页面打不开、需要登录、被限流或没有足够事件细节时，不要猜测。明确缺失内容，并请求用户导出最小必要数据（事件、伤害表、战斗元数据）；不要要求用户粘贴 API 密钥。若环境已有 WCL API 凭据，只从环境变量读取并绝不输出凭据值。

本地大文件优先用 `scripts/summarize_wcl.py` 生成紧凑摘要，再回看原始事件核对关键时间点。脚本是整理工具，不是自动判分器。

## 分析模式

根据用户目标选择一种或多种模式：

### 单场复盘

回答“我这把哪里损失最大”。先判断战斗是否可用，再按时间线、核心技能、目标和生存排序问题。

### 同场横向对比

回答“同一场另一个玩家为什么高/低”。优先比较同一战斗、同一团队环境下的玩家；同时检查职责分配、外部增益、目标和死亡时间，避免把不同任务当成操作差距。

### 高手样本提炼

回答“顶尖玩家通常怎么打”。筛选 3-5 个可比高分样本，使用中位数或稳定区间；不要用单个第一名样本代表唯一正确答案。

### 经验沉淀

把重复出现的规律写成“场景—触发条件—动作—原因—验证指标”经验卡。只有用户明确要求落盘时才修改仓库或本地文件；默认在回答中输出可复制的 Markdown 经验卡。

## 必守原则

1. **先校验战斗，再谈循环**：确认首领、难度、战斗时长、阶段、有效存活时间、死亡/掉线、目标数和团队战术。
2. **先做可比性筛选**：比较同首领、同难度、相近击杀时长、相同专精/英雄天赋/套装层数和相近装等区间的样本。无法满足时，明确写出偏差来源。
3. **不要只看总伤害**：同时看 DPS、存活时间、施法密度、核心技能次数、增益覆盖、目标分配、宠物/复制体伤害和关键阶段贡献。
4. **技能次数必须结合版本机制**：判断“漏按”前，先核对当前天赋、套装、饰品和热修；特别留意减冷却、充能、自动施加 DoT、爆发期间自动复制/转化等效果。不要把合理的延后、目标切换或自动触发误判成空窗。
5. **区分事实和推断**：每个主要结论都写“日志事实”“机制后果”“最可能原因”“下一把验证动作”，并标注置信度（高/中/低）。
6. **区分装备与执行**：装等、主属性、绿字、饰品和套装只作为背景；没有个人模拟时，不要声称某件装备精确造成了多少 DPS 差距。需要精确排序时建议 `/simc` 或 Raidbots。
7. **尊重团队任务**：打断、驱散、转火、减伤、站位和诱导机制可能牺牲个人伤害。只有在确认职责相同后，才把差距归因于输出手法。
8. **不把高分样本照搬给新手**：把结论拆成“理论上限、高手常用、新手容错、当前角色最值得练”四层。
9. **结论要能复核**：尽量给出相对战斗时间、技能次数、覆盖率、伤害占比或目标分配等证据；避免只说“感觉他更顺”。
10. **保护日志隐私**：不暴露 API 令牌、私密报告的隐藏信息或与问题无关的玩家数据；只引用完成分析所需的角色和战斗字段。

## 标准工作流

### 1. 建立战斗上下文

记录：报告、战斗编号、首领与难度、战斗起止时间、有效存活时间、玩家源 ID、专精/英雄天赋、套装、装等、饰品、团队人数、阶段和目标类型。若信息缺失，先按保守假设继续，并列出缺口。

### 2. 获取并压缩数据

- 在线：打开用户指定报告，优先获取战斗元数据、参与者、伤害表、施法事件、增益/减益事件和死亡事件；页面只显示排名时，不能假装已经看到了完整时间线。
- 本地：识别文件格式和时间戳单位，按 `fight`、`sourceID`、`targetID` 过滤；先运行本技能脚本生成摘要，再抽取关键时间窗原始事件。
- 多页事件：按时间戳排序、去重，并记录是否存在分页边界；分页缺失会影响施法间隔和覆盖率判断。

### 3. 选择基准玩家

基准优先级：

1. 同一场、同职责、同专精且任务相近的玩家。
2. 同首领/难度、相近装等和击杀时长的高分样本。
3. 多个样本的中位数与四分位区间。

高分样本必须记录：百分位或排名、装等、专精/英雄天赋、战斗时长、目标数、团队增益和是否存在特殊战术。若只能找到一个样本，称为“参考样本”，不要称为“标准答案”。

### 4. 做五层对比

按以下顺序，先找最大贡献再深挖细节：

1. **有效时间层**：死亡、掉线、跑位、无目标、阶段不可攻击和功能任务。
2. **战斗轴层**：药水/饰品/大招/套装/关键增益是否对齐到高价值阶段，理论可用次数和实际次数是否合理。
3. **循环层**：核心技能次数、施法间隔、公共冷却占用、资源生成/消耗/溢出、DoT/buff 覆盖。
4. **目标层**：主目标与小怪的伤害分配、顺劈/扩散、转火时机、快死目标上的铺垫、地面技能命中。
5. **构筑与装备层**：天赋节点、英雄天赋、套装、饰品、属性和外部增益；只有在前四层相近时，才把它作为主要解释。

### 5. 建立因果链

每个问题使用以下格式：

```text
日志事实：相对战斗时间 / 次数 / 占比 / 目标 / 事件
机制后果：它少触发、少复制、少覆盖或错过了哪个窗口
最可能原因：按键、战斗安排、目标选择、移动、职责或装备
下一把动作：只练一个可观察行为
验证指标：下一场在 WCL 看什么数字或时间点
置信度：高 / 中 / 低
```

不要把“相关”写成“确定因果”。例如某技能伤害低，可能是次数少、目标不同、增益不在身上、目标提前死亡或团队战术造成；必须用事件和目标拆分排除替代解释。

### 6. 输出和经验沉淀

先给 1-3 条最大损失，再给数据表和时间线证据，最后给下一把训练计划。经验总结优先写成可迁移规则，而不是某一把的按键录像：

```text
场景：首领 / 阶段 / 目标数 / 构筑
触发条件：何时进入这个窗口
动作顺序：中文技能名和必要的先后关系
机制原因：资源、增益、复制、覆盖或目标寿命
容错边界：什么时候应该延后、改目标或放弃
验证指标：次数、覆盖率、窗口伤害或死亡时间
来源：本地事件 / WCL 链接 / 指南 / 模拟
```

## 输出最低要求

一次完整复盘至少包含：

- 一句话结论：最大差距的 1-3 个来源。
- 战斗与样本背景：时长、存活、装等/套装、构筑和可比性。
- 对比表：DPS、有效时间、施法密度、核心技能次数、关键伤害来源、目标分配、生存。
- 时间线：开场、每次主要爆发和关键阶段；使用相对战斗时间，避免只写绝对时间戳。
- 因果分析：至少两条完整的“事实 → 机制 → 动作”链。
- 下一把训练计划：最多 2-3 个优先动作，每个有验证指标。
- 不确定性与遗漏数据：明确哪些结论需要更多事件、团队分工说明或个人模拟。

本地摘要工具：

```powershell
python scripts/summarize_wcl.py --events <events.json> --table <damage-table.json> --source-ids <id1>,<id2> --fight-id <fight>
```

可重复传入 `--events` 合并分页或不同玩家事件文件。若伤害表是带 `source` 参数导出的单角色表而没有事件文件，加上 `--table-source-scoped`；若只提供一种文件，省略另一参数即可。脚本会输出 JSON 摘要，无法从文件可靠推断的字段会标记为 `null` 或列入 `warnings`。
